## 1. 目的と既存仕様からの変更

現地LANに直接接続した調査用Windowsホストから、ボタン一つで収集可能な情報を集め、既存台帳との照合、機器・ネットワークのマッピング、監査結果の下書きまで作る。目視・管理画面・聞き取りが必要な箇所は、未確認の理由と次の確認方法を残す。

役割は **Nmap＝機器・ポート監査、TShark＝通信監査、PowerShell＝Windows・AD設定取得、Python＝実行・正規化・照合・統合** とする。パケットの解析はTSharkを利用し、Scapyや独自のプロトコル解析器は追加しない。

| 現行仕様・実装                                | 次期拡張での扱い                                                                                                                                  |
| --------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------- |
| 要件1.2：自動探索・通信キャプチャは初版対象外 | 現地監査モードで追加する。機器への設定投入・常時監視は含めない                                                                                    |
| 要件1・8：利用者にPython等の導入を要求しない  | 通常の編集・閲覧は維持。調査用ホストだけPython、Nmap、TShark/Npcapを準備する                                                                      |
| SEC-07・AC-02：アプリの外向き通信なし         | ブラウザーは既存のlocalhost窓口だけへ接続。収集プロセスだけがプロファイルで指定した社内対象へ通信する。インターネット・テレメトリー通信は行わない |
| 正本JSON、10MiB上限、厳格なスキーマ           | 大量の観測データは別ファイルに保持。正本には採用した資産・設定・証跡参照・監査結果を格納する                                                      |
| 4値判定、総括20項目、対象別結果、対応事項     | そのまま利用。収集の成否・観測の有無と監査判定を別管理する                                                                                        |
| 共有保存、競合検出、Undo、公開の許可リスト    | 正本保存はPowerShellの既存経路に一本化。Pythonは収集・証跡を担当し、正本を作成・更新・置換しない                                                  |

現行版の制約を黙って読み替えず、本計画を実装する段階で要件・基本設計・受入条件へ正式に反映する。AD情報の参照は追加するが、アプリのAD認証連携は追加しない。

## 2. 「その場でポチ」の操作

初回だけ、監査担当者が拠点プロファイルを作る。対象拠点・監査回次、NIC、CIDRと除外IP、調査強度、想定DNS/GW、承認DHCP、観測時間を登録する。未指定の基準は「基準未設定」と表示し、正常判定に使わない。

AD/DC・管理DHCP・証跡共有などの管理先は、走査対象と別の許可リストに登録する。標準の収集ではオンリンク外へのAD・DHCP・端末照会を行わず、必要なら詳細調査の経路承認に含める。証跡共有への保存は独立した保存操作として宛先・経路・利用ポートを表示し、走査の承認と混同しない。プロファイルの変更は次回実行から適用する。

従来の `tylan.cmd` → 今回のJSONを開く → 監査画面の **「現地監査を開始」** の1操作で、次を順に進める。標準モードでは追加承認を毎回要求せず、ボタンの近くに対象NIC・オンリンク範囲・除外・機能のON/OFF・所要時間の目安を表示する。Pythonが利用できないPCでも通常編集は継続できる。

1. ホスト・ツール・権限・NIC・出力先を確認し、実行時点の設定を固定する。
2. ローカル設定を取得し、TSharkの観測開始を確認する。
3. 受動観測だけの区間を取り、その後に指定範囲の探索・指定ポート監査を行う。
4. 収集できた情報を正規化し、基準・既存台帳・比較可能な前回実行と照合する。
5. 「新規機器候補／変更候補／異常候補／未確認と追加調査」を表示する。完了通知には失敗・除外・観測範囲も含める。
6. 担当者が差分を選び **「選択した結果を取り込む」**。証跡を共有へ転送・検証してから、台帳・設定・証跡参照・監査の下書き・取り込み記録を同じ正本JSONへ保存する。保存結果の照合まで終わって採用完了とする（6.3〜6.6）。

収集開始と正本への採用は別操作にする。新しい機器候補は自動で図のプレビューに現れるが、既存の手入力値や確認済み判定を収集だけで上書きしない。監査の最終確定は既存フォームで行う。共有への保存失敗と収集失敗も区別する。

### 2.1 実行プロファイルの初期値案

以下は実装・現地検証用の初期案であり、所要時間や網羅性を保証する値ではない。

| プロファイル | 自動で行うこと                                                                    | 初期制限                                                                                                                                                 |
| ------------ | --------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 標準現地監査 | ローカル設定、IPv4のARP/DNS/DHCP観測、オンリンクIPv4機器探索、指定TCPポート、照合 | 観測5分、冒頭30秒は能動調査なし。選択NICのオンリンクIPv4内で最大256アドレス、最大20ポート/ホスト。除外を先に適用。ジョブ全体15分で打ち切り、未完了を記録 |
| 通信だけ観測 | ローカル設定とIPv4のTShark観測。探索・DNSテスト・リモート照会なし                 | 5分。延長は実行条件に記録し、上限30分                                                                                                                    |
| 詳細調査     | 別サブネットのIPv4走査、サービス確認、追加ポート、任意のAD・DHCP・Windows照会     | 対象・NIC・送信元・選択経路・次ホップ・除外・方式・上限を実行ごとに提示し、明示的に承認。経路変更で承認失効                                              |

標準のTCPポート案は `22,53,80,135,139,443,445,515,631,3389,5985,5986,8080,8443,9100`。ポート番号からサービス名・機器種別を確定しない。プリンタ、カメラ、産業機器等は拠点に応じて除外・縮小する。全TCPポート、UDP総当たり、OS推定、NSE、`-A`、認証試行は標準に含めない。

複数サブネットは詳細調査で範囲・経路を個別に承認して分割実行する。「LAN全体」は登録した監査範囲を意味し、ルート表から到達可能な全ネットワークへ拡大しない。

### 2.2 IPv4監査とIPv6設定確認の切り替え

通信監査は初期版ではIPv4のみ。IPv6は運用対象外として、意図しない有効経路の有無を自ホストの設定から確認する。IPv6通信キャプチャ、DHCPv6/ICMPv6の解析、NS/NA・RAの観測、IPv6能動スキャンは詳細調査でも初期版の対象外とする。

| 設定                             | 初期値         | OFF・未対応時の表示                        |
| -------------------------------- | -------------- | ------------------------------------------ |
| IPv4機器探索                     | ON             | 機器探索未実施。通信で見えた候補だけ表示   |
| IPv4指定TCPポート監査            | ON             | ポート監査未実施                           |
| IPv4通信監査（ARP・DNS・DHCP）   | ON             | 通信監査未実施。各項目も個別にON/OFF可能   |
| IPv6ローカル設定確認（送信なし） | ON             | IPv6設定未確認。IPv6経路なしとは表示しない |
| IPv6キャプチャ／能動探索         | 初期版は未対応 | 有効化トグルを出さず「対象外機能」と説明   |

「IPv4のみ」は送信・キャプチャの対象を指し、IPv6ローカル設定確認は独立した読取操作である。OFFにした機能は実行条件・結果・次回比較へ残し、監査判定の「対象外」に自動変換しない。

## 3. 収集と画面の構成

```text
Edge / Svelte ── localhost・既存の合言葉/Host/Origin検査
       ▼
tylan.ps1：唯一のHTTP窓口・正本保存・取り込み確定
       │ 型付き要求をローカルへ置く／受付・状態・結果を読む
       ▼
Python job-owner：唯一の収集ジョブ所有者（HTTP・正本保存なし）
       ├─ PowerShell：固定したローカル設定／任意の管理情報取得
       ├─ TShark：指定NICのIPv4観測
       └─ Nmap：指定IPv4一覧の探索・ポート監査
       ▼
ローカル実行ディレクトリ：manifest / observations / findings / logs
       │ 必要な証跡を専用共有へ転送・完了確認
       ▼
差分プレビュー → 純粋な取り込み計画 → 証跡検証 → 条件付き正本保存 → 再読込照合
```

### 3.1 実装上の接続箇所

| 対象                                                                    | 変更計画                                                                                                                                                       |
| ----------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |

自動取り込みを行うMVPは `schemaVersion: 2` とする。0.1の「v1維持」を変更し、正本に `documentId` と `importBatches` を追加する（6.3）。大量の観測データは引き続き別形式。v1原本を維持して明示移行し、旧アプリはv2を拒否する。新規の今回分JSONは新しいdocumentIdを持ち、バックアップの復元・同一正本の移動は同じIDを保つ。

通常編集・監査編集は同じ画面・PowerShell保存経路を使う。PythonのHTTPホスト案は採用しない。Pythonを外しても保存機構は動き、v2対応と保存強化は通常編集にも適用する。

## 4. ツールごとの収集設計

### 4.1 PowerShell：最初に調査用ホストを把握する

ローカルのアダプター、IP/プレフィックス、ルート/GW、DNS、DHCPの有効状態・配布元・リース時刻、近隣キャッシュ、ドメイン参加状態を取得する。`Get-NetAdapter`、`Get-NetIPConfiguration -All`、`Get-NetIPAddress`、`Get-NetRoute`、`Get-DnsClientServerAddress`、`Get-NetNeighbor` と、必要属性に絞ったCIMを利用する。`Get-NetNeighbor` の内容は近隣キャッシュであり、LANの全機器一覧ではない。[IP設定](https://learn.microsoft.com/en-us/powershell/module/nettcpip/get-netipconfiguration?view=windowsserver2025-ps)、[近隣キャッシュ](https://learn.microsoft.com/en-us/powershell/module/nettcpip/get-netneighbor?view=windowsserver2025-ps)、[DHCP関連属性](https://learn.microsoft.com/en-us/windows/win32/cimwin32prov/win32-networkadapterconfiguration)

NICはWindowsのGUID・ifIndex・MACとTShark/Nmapのインターフェース一覧を突き合わせる。初回は候補を提示し、VPN・仮想NIC・Wi-Fi等を勝手に横断しない。実行中にNIC、IP、ルートが変わったら送信を止め、部分完了として再選択を案内する。自動検出したサブネットは対象範囲の候補にとどめる。

IPv6ローカル設定確認がONなら、送信を伴わない `Get-NetIPAddress -AddressFamily IPv6` と `Get-NetRoute -AddressFamily IPv6` から、自ホストのアドレス・NIC・状態・由来情報と `::/0` の次ホップ・メトリック・有効期間を記録する。調査NICの結果とVPN/仮想NIC等の結果を分け、既定のネットワークコンパートメントを対象とし、取得できない範囲を表示する。[IPv6アドレスの取得](https://learn.microsoft.com/en-us/powershell/module/nettcpip/get-netipaddress?view=windowsserver2025-ps)、[ルートの取得](https://learn.microsoft.com/en-us/powershell/module/nettcpip/get-netroute?view=windowsserver2025-ps)

IPv6運用基準が「未使用」の拠点で有効な `::/0` や想定外のグローバル/ULAアドレスがあれば、No.12の追加確認候補にする。リンクローカルアドレスだけで異常としない。RAはルーター・プレフィックス発見に関わるが、この設定取得だけでRAの送信者・不正RA・実際の業務通信・到達性を認定しない。採取時点の既定ルートなしも「LAN内にRAなし」を意味しない。IPv6の無効化・ルート削除は行わない。[IPv6 Neighbor Discovery](https://www.rfc-editor.org/rfc/rfc4861.html)

ADはRSATのActiveDirectoryモジュール、ドメイン疎通と読取権限がある場合だけ、指定ドメイン・OUに限定して `Get-ADComputer` の必要属性を取得する。ADの機器登録は現在の稼働・IP・端末設定を保証しない。対象Windows端末のIP/DNS/DHCP・OS等は、別途許可した端末リストに対するCIM/PowerShell Remotingで取得する。WinRMやFWを自動で有効化しない。[ADの検索範囲・属性指定](https://learn.microsoft.com/en-us/powershell/module/activedirectory/get-adcomputer)、[CIMのローカル・リモート取得](https://learn.microsoft.com/en-us/powershell/module/cimcmdlets/get-ciminstance?view=powershell-5.1)

DhcpServerモジュールと権限があれば承認サーバー、スコープ、除外、予約、リース、配布DNS/GWを読取取得する。`Get-DhcpServerInDC` はADで承認されたDHCPの一覧であり、ルーターや管理外のDHCPを含む全サーバーの検出器ではない。拠点の承認機器一覧も併用する。モジュールなし・権限不足は、その収集器だけをスキップして理由を残す。[承認DHCPの取得](https://learn.microsoft.com/en-us/powershell/module/dhcpserver/get-dhcpserverindc?view=windowsserver2025-ps)

出力は固定した属性のDTOを `ConvertTo-Json` で生成し、明示したUTF-8で書く。ローカライズされた表示表や `Format-Table` のテキストを主要な解析入力にしない。Wi-Fi秘密鍵、資格情報、ユーザー一覧、設定の全量ダンプは収集しない。

### 4.2 Nmap：登録した範囲で機器とポートを確認する

結果は `-oX` のXMLで取得し、標準出力の表示文言は解析しない。標準では検証済みEthernet/Npcap構成で `-sn -PR -n` のARP探索、`-sS -Pn -n -p <指定ポート>` のTCP監査を使う。選択NICのNmap名を `-e`、実在する送信元IPv4を `-S` で指定し、`--send-eth` を付ける。NIC指定だけに安全性を依存せず、下記の経路検証と組み合わせる。[探索方式](https://nmap.org/book/man-host-discovery.html)、[XML出力](https://nmap.org/book/output-formats-xml-output.html)、[Ethernet送信](https://nmap.org/book/man-misc-options.html)、[インターフェース・送信元指定](https://nmap.org/book/man-bypass-firewalls-ids.html)

0.1案の `-sT` はOSの `connect()` を使うため、`-e` の指定だけで送信経路を拘束できるとは扱わない。標準のraw送信が利用できない場合は能動収集をスキップし、受動観測・設定確認を続ける。権限の自動昇格、`-sT` への暗黙フォールバックは行わない。詳細モードで `-sT` を提供する場合もOS経路を別途承認し、指定NICへの拘束とは表示しない。[TCP connect scanの仕様](https://nmap.org/book/man-port-scanning-techniques.html)

探索で応答したIPに加え、既存台帳・DHCP等にある対象IPも照合する。探索に応答しなかった既知IPは、制限した別枠で `-Pn` の指定ポート確認を行えるようにし、未実施なら探索だけで見逃し得ると表示する。`open / closed / filtered`、応答理由、未走査・時間切れを保持し、応答なしを撤去・不存在へ変換しない。

送信速度・同時数・再試行・ホスト単位の時間を制限する。初期案は探索の `--max-rate 50`、TCP確認の `--max-parallelism 4` と `--scan-delay 100ms`、`--max-retries 1`、`--host-timeout 60s`。オプションの効き方は探索・走査方式で異なり、OSのTCP処理を含む厳密な全通信量上限とは扱わない。実測して調整し、上限による取りこぼしを記録する。[速度・再試行・タイムアウトの仕様](https://nmap.org/book/man-performance.html)

MAC/OUI、名前、開放ポートからの種別・メーカー推定は候補扱い。資産承認・所有者・型番・OS・脆弱性を自動確定しない。XMLはサイズ制限付きで解析し、DTD・外部実体・外部スタイルシートを取得しない。

#### 4.2.1 標準モードの送信条件と変更時の停止

1. 選択した物理Ethernet NICのGUID、ifIndex、MAC、有効な送信元IPv4、プレフィックスを固定する。VPN/トンネルは標準対象にせず、複数IPv4があれば送信元を選ぶ。
2. 対象を「登録CIDR ∩ 選択送信元のオンリンク範囲 − 除外」として具体的なIPv4一覧へ展開する。network/broadcast、自ホスト、multicast等の不適切な対象を除き、上限超過・範囲外の要求は黙って広げず拒否する。
3. **NICで絞る前の** Windowsの最適経路を各宛先について取得し、選択NIC・送信元と一致し、次ホップが `0.0.0.0` のオンリンクであることを確認する。より具体的な `/32` やVPN向け経路、別NIC優先、等コストで一意に選べない経路は拒否する。NICを指定して調べた経路だけでは、OSの実際の選択の検証にならない。[Find-NetRoute](https://learn.microsoft.com/en-us/powershell/module/nettcpip/find-netroute?view=windowsserver2025-ps)
4. `nmap --iflist` のNIC・送信元・経路表示とも照合する。不一致・解析不能・未検証のツール版なら送信しない。対象一覧は固定ファイルにし、ホスト名や発見した別IPをその場で追加しない。
5. 送信は最大16宛先・10秒程度の小バッチに分け、開始前に経路・NIC・送信元の指紋を再検証する。実行中はWindowsのアドレス/経路変更通知を監視し、補助の定期再確認も行う。関連経路が変わったら現在のNmapを停止し、新しいバッチを起動しない。変更前後の指紋と未実施対象を残す。

例：ホストが `192.168.10.20/24` でも、`192.168.10.50/32` がVPNを向けば標準の送信条件に違反する。全範囲へ先に走査してから検出する方式は取らない。

これらは送信範囲を制御するアプリの条件であり、ドライバー・OS・ネットワーク機器まで含めた完全な隔離の保証ではない。通知から停止までに送信済みのパケットは取り消せない。P0では複数NIC・VPN・ホストルート・経路変更を再現し、別NICの観測点も使って実際の出力先を検証する。経路保証を厳密に求める現場では、管理側で分離した調査ネットワークを使う。

#### 4.2.2 詳細モードの経路承認

承認画面は、具体的な対象一覧/範囲、除外、NIC・送信元、宛先ごとの経路プレフィックス・次ホップ、方式、ポート、上限をまとめた `executionPlanHash` を提示する。承認はその実行だけに有効とし、承認後にどれかが変われば開始を拒否する。実行中の変更は停止し、再承認なしに続行・別GWへの切り替えをしない。AD等の照会もこの計画へ含め、ツールが別宛先へリダイレクトする場合は未承認先への接続を止める。

### 4.3 TShark：観測できた通信から事実を得る

初回診断は `tshark -v`、`-D`、`-G fields` を使い、Npcap・キャプチャ権限・必要フィールドの存在を確かめる。Wiresharkが導入済みでも、TSharkの導入や実際のキャプチャ成功は別に確認する。実行は `-n` で名前解決を抑え、`-a duration:300` 等で終了させる。キャプチャフィルター `-f` と表示フィルター `-Y` を混同しない。[TSharkのオプション](https://www.wireshark.org/docs/man-pages/tshark.html)

MVPの通信監査はIPv4のARP、平文DNS、DHCPv4だけを対象とする。全項目ONの場合のキャプチャフィルターは `arp or (ip and (port 53 or (udp and (port 67 or port 68))))` とする。IPv4を示す `ip` 条件を明示し、IPv6上のDNSも含めない。DHCPv6の546/547、ICMPv6のNS/NA・RAは追加しない。項目のON/OFFから固定テンプレートでフィルターと抽出フィールドを生成し、全OFFならTSharkを起動しない。UIから自由なフィルター文字列は受け付けない。キャプチャの `-f` の仕様と実機サンプルで検証する。[TSharkのフィルター指定](https://www.wireshark.org/docs/man-pages/tshark.html)

VLANタグ等を伴う観測点では別の検証済みIPv4フィルターを使い、取りこぼす条件を残す。一般ポート用フィルターをSPAN/TAPへそのまま流用して網羅性を主張しない。

`-T fields` の許可したフィールドだけをストリームで読み、時刻、NIC、IP/MAC、DNS応答コード・問い合わせ/応答対応、DHCPメッセージ種別・server identifier・配布情報を正規化する。フィールド名は実機の一覧と互換表で解決する。DHCPv4の現行フィールドは `dhcp.*` であり、古い名称の固定に依存しない。[DHCPフィールド参照](https://www.wireshark.org/docs/dfref/d/dhcp.html)

標準ではpcapng本体・任意ペイロードを保存しない。DNS名は対応付け後に既定で集計へ落とし、詳細保存を選んだ場合だけ証跡へ残す。フィールド出力の繰返し・空値・引用・制御文字は固定した形式で解析する。生キャプチャが必要なプロファイルでは、期間・サイズ上限・専用ACL・保持期間を設定し、標準のJSONや閲覧HTMLに内包しない。フィルターを掛けても生パケットに秘密や個人情報が入り得るため、秘密を除去済みとは表示しない。

開始/終了時刻、実観測秒数、パケット件数、フィルター、アダプター、ドロップ件数または「取得不能」を記録する。0件・権限不足・途中終了・出力解析失敗を区別する。

### 4.4 観測点と自分の調査通信

スイッチ配下の通常ポートでは、主に自ホストとの通信と到達したブロードキャスト等を観測する。他端末同士のユニキャスト、別VLAN、暗号化されたDNSの中身まで見えるとはしない。他端末間も見るには、管理者が用意するSPAN/TAPや対象端末での収集が必要となる。[WiresharkのEthernet観測条件](https://wiki.wireshark.org/CaptureSetup/Ethernet)

実行結果に観測点を `host / span / tap / imported` として残す。接続VLAN、SPAN対象が不明なら不明と記録し、観測できた範囲以上に判定を拡張しない。

標準は冒頭30秒の受動区間と、その後の能動調査併用区間を分ける。NmapやDNSテストの実行時刻・送信元・対象を記録し、自分の調査による通信を可能な範囲で分類する。分類不能な通信は不明のまま保持し、通常時の異常率から除外または別集計する。名前解決のための意図しない追加通信は抑止する。

## 5. 観測・評価・最終判定を分ける

### 5.1 収集状態と網羅性

| 軸         | 値・記録                                                                                                                                      |
| ---------- | --------------------------------------------------------------------------------------------------------------------------------------------- |
| ジョブ状態 | `queued / running / cancelling / completed / partial / failed / cancelled / interrupted`。段階は別属性とする（8.1）                           |
| 収集器状態 | `completed / failed / skipped / timedOut / cancelled / truncated` と理由。`truncated` は容量・件数上限での打ち切り。正常終了でも0件はあり得る |
| 観測状態   | `observed / notObserved / unknown`。対象事象を見たか、観測を成立させたかを区別する                                                            |
| 評価       | `finding / noFindingInScope / inconclusive / notApplicable` とルールID・根拠・制約                                                            |
| 監査判定   | 既存の `unchecked / ok / ng / na`。評価から無条件に自動変換しない                                                                             |

範囲は拠点、NIC/観測点、セグメント、対象ホスト、IPファミリー、ポート/プロトコル、期間、除外、未実施・失敗を持つ。ホスト数・走査済み対象数等は実数と分母を表示する。受動観測に「LAN全体の検出率100%」のような数値を作らない。

### 5.2 初期の検出・判定ルール

| 事象                             | 自動生成する情報                                              | 判定上の制約・追加確認                                                                                                            |
| -------------------------------- | ------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| DHCP通信が0件                    | 「5分観測、DHCP応答未観測」、観測条件、追加調査               | No.13・14は原則未確認。30秒でも30分でも不存在の証明にならない。配布元設定・リース・別の観測点を確認                               |
| 複数DHCPからOFFER/ACK            | サーバー識別子、送信元、relay情報、配布DNS/GW、時間帯を一覧化 | 正規の冗長構成・relayを考慮。承認リストとの差異を異常候補にし、複数という理由だけで不正認定しない                                 |
| 承認外DHCP候補                   | 有効な基準にない配布元と、観測した応答の証跡                  | 基準の鮮度・ルーターDHCP等を確認し、確認者・問題点・対応事項を付けてNo.14の要対応を確定                                           |
| IPと複数MACの対応                | 同一観測セグメント・時間帯の対応変化、出典                    | IP再利用、冗長GW、proxy ARP、仮想化を除外できるまで重複/ARP偽装の候補。時刻やセグメント不明なら断定しない                         |
| 169.254.x.x                      | 設定または通信で確認したIPとNIC                               | 意図したリンクローカル用途を照合。通常LANでのDHCP不調等の候補とし、用途不明なら未確認                                             |
| 想定外DNS設定・宛先              | ホスト設定、配布DNS、観測DNS宛先と基準との差分                | 承認基準がない場合は基準未設定。自ホストの結果を全端末へ一般化しない                                                              |
| DNSのNXDOMAIN/SERVFAIL/無応答    | コード別件数、対応付け可能な問い合わせ数、応答遅延、観測範囲  | NXDOMAIN単発を障害としない。再送を整理し、観測終了間際・ドロップ・キャッシュ・DoH/DoTの不可視性を考慮。閾値未設定なら統計だけ提示 |
| 台帳にないIP/MAC・新規開放ポート | 新規/変更候補、プロトコル・状態・理由・前回との差             | 未登録と非承認を分離。開放ポートだけで脆弱性としない。承認基準とサービス用途を確認                                                |
| 前回見えた機器が今回見えない     | 「今回未観測」と比較条件の差                                  | 電源断・FW・観測漏れ等があり得る。撤去・長期未使用の自動判定、台帳削除はしない                                                    |

最終判定の初期値は未確認。取り込み時には `finding / method / evidenceIds`、実施した場合の `attempted / reason / nextCheck` を下書きにする。問題なしには対象範囲を含む確認結果・確認者・確認日、要対応にはさらに問題点と対応事項、対象外には実際の適用外理由を要求する。失敗・未観測を対象外に変えない。

既に確定した判定と矛盾する証拠が出た場合は、その場で確定値を上書きせず再確認候補として表示する。拠点総括は既存どおり20件が分母で、個別結果の未確認・要対応を隠して問題なしにはできない。

## 6. 自動マッピングと同一機器の照合

### 6.1 自動化できる図の範囲

初期の自動マップは、発見した機器候補、セグメント所属候補、DNS/DHCP/GWの役割・利用関係を表す論理マップとする。正本に採用した機器は既存の図へ追加できる。セグメント別の候補表示はプレビュー側で行い、未採用候補を実在資産として混入させない。

Nmap・ARP・DNSだけから、サービスアダプタ→スイッチ→AP→端末という物理配線、スイッチのポート番号、空きポート、VLANタグ、無線の接続先APを確定しない。管理IPを持たないL2機器は見つからないことがある。

実際に観測したDNS等の利用関係を正本の `links` に採用する場合は `kind: logical` とし、根拠に応じて `certainty` を指定する。物理ポートが分からない端点は `portId: null` とする。IP格納のためにポートが必要な場合は「観測IF（名称未確認）」として作り、物理媒体・速度・使用状態を推測で埋めない。所属関係だけで全機器とGWの配線を描かない。

物理構成の自動化は次段階で、管理スイッチのLLDP/CDP隣接・MACテーブル・ポート/VLAN情報の読取取得や、管理画面エクスポートを足す。MACテーブルも配下にハブ等があり得るため、直接配線の証明として単独採用しない。MVPでは目視確認を補助する未確認一覧を生成する。

### 6.2 同一性・取り込み・再実行

- 拠点・セグメント・観測時刻を含めてIP/MACを扱う。別VLANの同一IP、DHCPでのIP再利用、多NIC、仮想MAC・ランダムMACを考慮する。
- 既存の機器IDへの明示対応を優先し、信頼できる資産番号・シリアル・ADのobjectGUID等を照合根拠とする。IPだけ・名前だけ・OUIだけでは既存資産を自動統合しない。MAC一致も候補とし、矛盾があれば選択を求める。
- 各値に出典・時刻・観測/設定/推定の別を付けて競合表示する。端末から読んだDNS設定と台帳の想定DNSを一方で消さない。
- 新規IDは既存形式を守り、照合台帳に観測キーと採用先IDを保存する。同一run・観測キーの再取り込みで資産・証跡・監査結果を重複生成しない。
- 照合台帳だけを採用済みの根拠にせず、正本に残る採用先ID・証跡参照も検証する。Undo・正本差し戻し・転送失敗後は現状から計画を再作成し、取り込み記録との不一致を表示する。
- プレビュー時のDoc指紋とrevisionを記録し、適用時に変わっていれば差分を再評価する。採用内容は1回の確定とし、共有の競合時は既存処理で保存を止める。

### 6.3 正本の取り込み記録を確定の根拠にする

証跡共有と正本JSONをまたぐ単一トランザクションは作らない。**検証済み証跡が先、参照を含む正本保存が後**という順序に固定し、未参照の証跡が残ることを許容する。参照先未完成の状態を通常の採用結果として保存しない。

v2では次を正本に追加する。別ファイルのImportReceiptは実行経過の補助であり、採用済み判定の唯一の根拠にしない。

| 属性                                                    | 役割・制約                                                                                                                    |
| ------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------- |
| `documentId`                                            | 正本の論理的なID。projectIdやファイル名だけに依存しない。同一正本の復元は維持し、別の監査用JSONを作るときは新規発行           |
| `importBatches[].id`                                    | 採用操作ごとのimportId。準備時に固定し、保存再試行・応答消失後の照合でも再発行しない                                          |
| `runId / packageHash / selectionHash`                   | 元の観測・封印済み証跡・選択内容を特定する。IDだけが同じで内容が異なればエラー                                                |
| `state`                                                 | `applied / reverted`。保存中・保存失敗は正本の確定状態にせず、ホスト側の操作状態として持つ                                    |
| `bindings`                                              | 観測キー→採用先コレクション/ID/対象フィールドの対応、生成ID、採用時の値のハッシュ。部分取り込み・重複する選択も照合可能にする |
| `evidenceIds / intentReference / checkedBy / appliedAt` | 正本内証跡への対応、封印済み採用計画の参照、担当者・日時                                                                      |

観測キーはrun内の安定した観測ID＋採用対象の区分/フィールドとし、IPだけをキーにしない。同じrunの同じ観測から別の意図で複数の対象を作る場合は、区分を明示する。別runの同一機器は6.2の同一性照合を通す。

取り込み済みの観測キーは既存bindingsを再利用する。既存機器に採用済みのフィールドがその後手修正されても、再送で元に戻さない。対応先が削除・変更されていれば再照合を要求する。bindingsは来歴なので、過去の採用先が現存しない状態も「削除済み/要再照合」として扱い、機器を勝手に再生成しない。

正本内の記録と実体の参照・重複を検証し、記録の肥大化も10MiB制限へ算入する。上限時は取り込みを分割または回次を分け、履歴を黙って捨てない。v1からの移行・バックアップ・公開用射影の除外・旧版拒否もP3の必須作業にする。

### 6.4 証跡先行の採用手順

1. **画面の保存を整える。** 未保存編集をflushし、保存済み・競合なしを確認する。以後、採用完了/失敗確定まで新規編集・通常自動保存・別の採用・Undoを直列化する。元JSONのdocumentId、revision、ファイル全体のSHA-256、更新トークンを固定する。
2. **証跡を確定する。** 7.2の手順で証跡共有へ転送し、全ファイルの長さとSHA-256を再読込検証する。まだ転送できなければ `evidencePending` で止め、正本の業務データ・証跡参照は更新しない。ローカル結果の閲覧・再転送は可能。
3. **採用計画を準備する。** TSの純粋関数が差分・固定の生成ID・importIdを作り、`validate` を通す。`POST /api/imports/prepare` へrunId、選択、明示対応、元指紋、固定ID、候補JSONを渡す。PowerShellは元指紋・要求上限を検証し、固定計画を自分の採用記録へ保存する。Pythonへ `PrepareEvidence` を依頼し、選択・対応・差分ハッシュを記したintentも専用証跡領域へ先行保存・検証させる。APIは待たず202を返し、画面は準備状態を取得する。
4. **正本を保存する。** Pythonから候補ハッシュ・documentId・importId・packageHashに結び付く新鮮な `VerifyEvidence` 応答を取得した後、PowerShellが短寿命prepareTokenを発行する。`POST /api/imports/{importId}/commit` で固定計画・証跡検証応答・セッションを照合し、共通 `Save-Canonical` の保存キュー内で現在の指紋を再確認する。差があれば409で止め、上書きへ切り替えない。
5. **一つのJSONを置き換える。** 業務差分・証跡参照・`importBatches[state=applied]` を同じ候補に含め、同じ共有ディレクトリの一時ファイルへ完全に書く。再読込・JSON検証・ハッシュ検証後、旧版を退避して置換する。置換を提供できない共有では失敗にし、既存ランチャーにある `File.Replace` 失敗時の上書きコピーにはフォールバックしない。
6. **保存結果を照合する。** 正本を読み直し、候補ハッシュとimportId・packageHash・bindingsを確認して初めて保存成功を返す。UIは確認した正本に差し替え、Undoフレームを登録する。ImportReceiptは後から更新でき、失敗しても正本の採用記録から再構築する。

Python側へ別の照合・正本保存アルゴリズムは実装しない。業務の構造・参照検証はTS Coreで行い、PowerShellは入力上限・正本指紋・固定候補ハッシュ・取り込み記録・検証応答を確認する。汎用PUTによる新しいbatch/自動証跡参照の追加は拒否し、prepare/commitを通す。Pythonへ渡すのは選択・証跡manifest・intent用メタデータだけで、正本の書込先や保存命令はIPCの型に含めない。

検証応答はownerEpoch・requestId・nonce・候補ハッシュ・証跡ハッシュ・検証日時・期限を含み、起動時にIPC用ACL下で共有した秘密でHMACを付ける。HTTPの合言葉や秘密そのものはPythonの結果へ書かない。有効期間の初期値は5秒。期限切れなら非同期で再検証し、新しい応答を待つ。最終確認から保存までの外部削除は排除できないが、古い転送完了通知だけではcommitを許可しない。

準備以降の内容変更はtokenを破棄して再準備し、同じ採用操作の単純再送は同じimportIdで照合する。採用準備・通常保存・証跡タスクは別状態であり、PowerShellは収集ジョブの状態遷移を実装しない。

ファイル指紋の再確認と置換だけでは、他PCの非協調書き込みまで原子的に比較交換できない。編集者1名の運用を維持し、同一PowerShell窓口の保存を直列化する。最終照合で別内容なら成功とせず `saveUnknown` とし、旧版・一時候補・証跡を残す。共有の置換動作・切断時の結果はP0で実測し、対応外の共有で採用を有効化しない。

通常の編集・Undoで追加するv2保存も条件付き置換と再読込照合を使う。`exportJson()` が書込前にcleanへ変える現行実装は、**候補の準備**と**保存確認後の採用**に分ける。保存要求を送れたことだけでrevision確定・保存済み・採用完了にしない。

### 6.5 失敗と応答消失からの復旧

| 状況                            | 正本・証跡の状態                             | 次の動作                                                                                                                                                                |
| ------------------------------- | -------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 証跡転送中に失敗                | 正本未変更。一時証跡は未封印                 | 同じpackageHashで転送再試行。未検証の証跡は採用しない                                                                                                                   |
| 証跡確定後にJSON保存失敗        | 証跡は存在、正本は旧版または結果不明         | 正本を再読込。未採用なら同じ証跡・importId・生成IDで再準備。不要な再転送・資産生成はしない                                                                              |
| 保存の応答が消失                | JSON保存済みか不明                           | 自動でcommitを再送しない。まずdocumentId・importId・packageHash・bindingsを読む。適用済みなら成功へ回復。存在せず元指紋一致なら同じ操作を再試行。別内容なら差分を再作成 |
| 保存競合                        | 他の変更がある正本と封印済み証跡             | 正本を読み直して既存bindingsと手入力値を再照合。再確認した計画だけ新tokenで準備し、既存の証跡と安定IDを再利用する                                                       |
| 正本保存成功、Receipt更新失敗   | 正本に採用記録あり、別ファイルの状態だけ古い | 正本を優先しReceiptを再構築。採用処理は実行し直さない                                                                                                                   |
| 正本保存後に証跡が欠損/破損     | 初回採用後の外部削除・障害                   | 「証跡参照不整合」を表示。ローカル保全物から同一ハッシュの内容だけ復元。復元不能なら要再調査として残し、無言差し替えや正常表示をしない                                  |
| 正本の書込/置換結果が壊れている | 旧版・候補・証跡が保全されている             | 自動再走査・再取り込みを停止。既存の復旧手順で正本を検証して戻し、その後採用記録を照合する                                                                              |
| JSONを旧版へ戻した              | documentIdは同じでも採用記録がない/古い      | Receiptを根拠に適用済みとしない。「正本差し戻し・再確認待ち」として再プレビュー。封印済み証跡は再利用できる                                                             |

「JSON保存成功、証跡転送失敗」は通常の手順では発生させない。証跡の検証前にはcommitを許可しない。ただし、検証後の共有障害・外部削除まで分散トランザクションで防げるとはしない。

再試行時、同じimportIdで別packageHash/選択内容が送られたら409で拒否する。計画変更で新importIdを作る場合も、正本内の観測キーを調べて既に採用済みの機器・証跡・監査結果を再利用する。部分採用で選択が重なっても二重に生成しない。

### 6.6 Undoと未参照証跡の扱い

Undoは業務データの変更を戻し、証跡共有のファイルを削除しない。取り込みを戻した記録は正本の `importBatches` に `reverted` として保持し、元の生成ID・証跡・観測キーの対応を残す。再採用は明示操作とし、同じ安定IDを再利用できるか現在の正本で検証する。

現行の全Docスナップショット復元をそのまま使うと記録が消えるため、Undoフレームに操作種別とimportIdを保持する。通常編集のUndoは現在の取り込み履歴を保ったまま業務スナップショットを復元し、取り込み自体のUndoだけ該当batchをrevertedへ遷移させる。後続操作は通常の順序で先に戻し、途中の取り込みだけを抜き取る選択的UndoはMVP対象外。復元後も参照整合性・監査必須欄を検証し、通常の条件付き保存で確定する。失敗/不明時は6.5と同様に照合する。

UI内のUndoは従来どおり10世代・同一セッション内とし、永続の採用記録を無期限Undo機能とは扱わない。保存後の再読込・復旧では履歴を見て採用状態を説明できるが、過去の変更を勝手に逆適用しない。

証跡先行・取消・中断により残るファイルは「既知の正本から未参照の候補」として一覧化する。別の正本コピー・archive・バックアップが参照している可能性があるため、Undo・保存失敗・run終了を契機に自動削除しない。削除は保持期間と既知の全参照先を確認した管理操作とし、参照先の網羅性を確認できなければ保留する。保持期間未設定時は削除しない。削除後もpackageHash・理由・担当者・日時の記録を残す。

### 7.2 保存場所と容量

作業中は調査用ホストの `%LOCALAPPDATA%\tylan\audit-runs\<runId>\` 等、実行ユーザーに限定した場所へ書く。共有障害でも取得済み結果を維持する。収集の最終化後に内容を固定し、相対パス・長さ・SHA-256の一覧を持つmanifestからpackageHashを作る。変化する進捗・Receiptは封印対象から分ける。

証跡本体は専用共有 `evidence\<siteId>\<runId>\<packageHash>\` へ転送する。固定配下の一時領域へ書き、共有から全ファイルを再読込・ハッシュ検証した後、manifestHashを含む `SEALED.json` を最後に作り再読込確認する。**SEALEDと実体の検証が揃って初めて採用可能**。途中転送先は一覧でも未完了とする。既存の同一パッケージは検証して再利用し、同じパスに異なる内容があれば上書きせず破損として止める。封印済み内容は変更・追記せず、別の内容は新packageHashにする。

採用intentは `evidence\<siteId>\imports\<importId>\<planHash>\` に同様の手順で保存する。再準備した別planも上書きしない。各ファイルのパスはサーバー側生成とし、manifestの `..`・絶対パス・再解析ポイント等による領域外参照を拒否する。保存直前にもSEALEDと必要な全証跡を検証し、長寿命の「存在確認済み」キャッシュだけで採用を許可しない。

正本の `evidence` には説明・管理番号・検証済み共有保管先・取得日・取得者を格納する。転送できない結果はローカルの実行一覧に保留し、存在しない共有参照や一時的なローカルパスを自動採用しない。証跡パスは文字列として扱い自動実行しない。ローカル保全物は転送成功だけで削除せず、保持規則に従って欠損復旧に利用する。

現在のランチャーは4フォルダーと `.json/.html/.csv` のみを許可するため、汎用ファイルAPIの許可範囲を広げない。監査専用APIが既知の実行IDに対して小さな統合結果だけ返す。証跡転送はPythonの専用タスクが固定先へ行い、任意のパスをブラウザーから受け取らない。

初期上限案は、実行ディレクトリ合計200MiB、標準の統合結果10MiB、観測10万件。上限到達時は打ち切り・集計へ移行し、欠落・集約件数を明示する。任意の生キャプチャはこの容量内で最大100MiB・30分に制限する。大きい実行は分割し、正本10MiB上限を別途検証する。生データを自動で削除して空きを作らず、保持・削除は設定した運用に従う。

公開HTML・通常CSVには、生キャプチャ、内部ログ、照合台帳、未採用観測、秘密を含み得る詳細データを追加しない。採用した監査の文章も既存の公開範囲プレビューで確認する。

### 7.3 調査用ホストの準備

Pythonの対応版を実装時に固定し、通常のCPython＋少数の依存で始める。Python、Nmap、TShark/dumpcap、Npcap、PowerShellモジュールの実体パス・版・機能・権限を診断する。未導入のソフトを実行時にダウンロード・自動インストールしない。Wireshark既設のTShark/Npcapは再利用し、同梱の要否とライセンスは配布形態を決める際に確認する。

調査機能は通常編集と切り離し、Python等がないPCでも既存の編集・閲覧を利用できるようにする。権限不足は自動昇格や設定変更で回避せず、可能な収集器を続行して不足を報告する。標準の画面・ランチャー全体を管理者として常用する方式にはしない。

## 8. 実行の所有権・停止・再起動

### 8.1 保存とジョブの所有者を分け、保存実装は一つにする

PowerShellはHTTP・セッション・正本保存・採用確定、Python job-ownerは収集タスク・子孫プロセス・証跡転送/検証を担当する。PythonはHTTP待受けや正本保存APIを実装しない。PowerShellはPythonを固定引数で起動するだけで、収集器のプロセスハンドル、PIDのkill、Job Object、ジョブの終了判定を持たない。

プロセス間連携は残るが、業務JSONの保存実装を複製する代わりに、下記の有限な要求/応答プロトコルだけを増やす。正本保存の失敗はPowerShell、収集の失敗はPythonが報告し、互いの状態を推測して書き換えない。

Pythonは実行ユーザーに制限したnamed mutexで多重起動を拒否する。MVPは調査ホストの実行ユーザー・監査用セッションを各1つとし、同時収集は1件、待ち行列は設けない。別ユーザーをまたぐ複数管理者運用は対応条件に含めない。

| 管理対象                               | 唯一の所有者・保存方法                                                                                                 |
| -------------------------------------- | ---------------------------------------------------------------------------------------------------------------------- |
| HTTPセッション・prepareToken・採用操作 | PowerShell。既存の256ビット合言葉・Host/Origin検査を利用し、秘密はログへ残さない                                       |
| 正本書込・競合検出・置換・保存照合     | PowerShellの共通 `Save-Canonical`。通常編集/自動保存/採用/Undoの全経路をここへ集約                                     |
| 収集状態・子プロセス・OSハンドル       | Python JobManager。状態遷移をイベントループ上で直列化                                                                  |
| runの永続スナップショット              | Pythonだけが `state.json.tmp → state.json` で保存。runId、ownerEpoch、状態、段階、sequence、最終更新、期限、理由を記録 |
| 証跡の転送・封印・検証結果             | Pythonだけが書く。PowerShellは内容に結び付いた検証応答を確認して採用を許可する                                         |

ジョブ状態は `queued → running → completed / partial / failed`、停止は `running → cancelling → cancelled`。異常終了は次の所有者が `interrupted` として回収する。段階は `validating / observing / scanning / finalizing` 等の別属性。終了状態は上書きせず、再実行は新runIdにする。PowerShell側の「依頼済み・受付未確認」はジョブ状態と分ける。

進捗ファイルは復旧材料であり、生存証明ではない。PythonはOSハンドルの実状態を優先し、状態保存失敗時は新規送信を止める。PowerShellは古いrunningやハートビートだけで実行中/停止済みを確定しない。共有転送・解析はPython側の有界タスクへ逃がし、IPCのCancelRunをブロックしない。

#### IPC：型付き要求と一方向の状態公開

IPC先は `%LOCALAPPDATA%\tylan\audit-ipc\<ownerEpoch>\`。所有ユーザーとSYSTEMに限定したACLを適用し、ブラウザーからファイル名・パス・コマンドを指定させない。PowerShellが要求とlease、Pythonが受付応答・状態・結果だけを書く。各ファイルは一時書込後の置換で公開し、共有上のファイルをIPCにしない。

要求は `protocolVersion / ownerEpoch / sessionId / requestId / idempotencyKey / kind / payloadHash / nonce / issuedAt / expiresAt / payload`。種類は `StartRun / CancelRun / PrepareEvidence / VerifyEvidence` に限定する。任意コード・シェル文字列・正本保存命令は型に含めない。型・件数・長さ・版・期限・所有epochを両側で検証し、未知の種類は拒否する。

1. 初回の監査要求でPowerShellが専用epoch・起動nonce・IPC用秘密を生成してPythonを非表示起動する。Pythonはmutex取得・復旧検査後に一致するready応答を出す。HTTP側は起動待ちで止まらず、依頼IDと「起動/受付未確認」を202で返す。
2. ready確認後の要求は固定runId・実行キーで保存する。Pythonは入力ハッシュと重複台帳を永続化してから受付応答を出し、その後に子プロセスを起動する。同キー/同内容は同run、内容違いは競合。同時に別runがあれば拒否する。
3. PowerShellは受付・状態・結果のスナップショットを短時間で読みHTTPへ返す。応答が遅くても監査失敗や停止済みと決めず「受付/状態確認不能」。同じキーで照会・再送し、新runや別Pythonを自動起動しない。
4. CancelRunは繰返し可能。開始と停止の到着順が逆でも、PythonがrunIdの取消記録を先に保存し、遅れて届くStartRunを実行しない。受付前の取消も同じ扱いとする。
5. 古いepoch、期限切れ、壊れた要求は実行しない。新セッションは古い要求を再生せず、過去runと正本を照合してから明示再実行する。requestIdと内容ハッシュの対応を保持し、応答ファイルの重複から副作用を再実行しない。

起動失敗・mutex競合・プロトコル不一致はそれぞれ返し、Python不在でも既存の編集・保存は継続する。IPCの期限切れは新しい採用準備を止める理由であり、既に保存された正本を巻き戻す理由にはしない。

### 8.2 子孫プロセスの停止を一か所に閉じ込める

固定したNmap/TShark/PowerShellだけを引数配列で起動し、シェル文字列・任意の追加引数・スクリプト・出力先を受け付けない。通常の呼び出しは `shell=False`、Windowsの起動/停止だけは `windows_process.py` の小さなWin32ラッパーに閉じ込める。[Python subprocess](https://docs.python.org/3/library/subprocess.html)

runごとにWindows Job Objectを作り、`JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` を設定する。ルートの収集プロセスをsuspendedで生成し、Jobへ割り当ててから再開する。JobハンドルはPython job-ownerだけが保持し、子へ継承せず、breakawayを認めない。TSharkが生成するdumpcap等も同じJobに入ることをP0で確認する。割当失敗なら再開せず終了し、能動調査を始めない。[Job Objects](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects)

キャンセル・期限・経路変化では新しい起動を即時停止し、ツール別の正常終了手段を最大5秒待つ。終了しなければ該当Jobを終了し、子孫が0件になったことを確認して部分結果を最終化する。同名プロセスの一括終了、状態ファイルに残るPIDだけを使ったkillは行わない。全体期限・収集器期限・容量を監視し、stdout/stderrは上限付きで並行に読む。

Job Object自体はなくさず、実装箇所と所有者をPythonの一か所にする。job-owner異常終了時の子孫停止を保証できない代替実装では能動監査を有効にしない。中断XMLや途中の抽出結果は、その完全性を検証できた部分だけをpartialとして扱う。

### 8.3 寿命を同期させず、切断後の動作を固定する

PowerShellは監査用セッションが生きている間だけ、IPCへ30秒ごとのleaseを更新する。Python側のlease期限は90秒を初期値とする。leaseは新しい要求の受付とアイドル終了の判断用であり、収集器を直接killする命令やジョブ生存証明ではない。

| 事象                         | 動作                                                                                                                                                    |
| ---------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------- |
| ブラウザー再読込・一時切断   | 同一PowerShellセッションから状態を再取得。開始ボタンの再送で新runを作らない                                                                             |
| ブラウザー終了               | PowerShellは従来の3分アイドルで終了してよい。進行中runはPythonが既定の全体期限まで収集し、ローカルへ最終化。採用を自動実行しない                        |
| PowerShell終了・lease失効    | Pythonは新要求を拒否。進行中収集は期限内で最終化し、進行中証跡転送は別の有限期限内で完了/中断する。仕事がなければ終了し、常駐しない                     |
| 明示的な監査中止             | PowerShellがCancelRunを置き、Pythonが停止する。PowerShell終了で停止を代替しない                                                                         |
| Pythonの通常終了             | 新要求を止め、残る子孫を停止・回収し、状態保存後にmutexを解放                                                                                           |
| Pythonのクラッシュ・強制終了 | Jobハンドル終了により子孫を停止。PowerShellは状態確認不能と表示し、正本保存は通常どおり利用可能                                                         |
| OS再起動・新ownerEpoch       | Pythonがmutex取得後に旧非終了runをinterruptedとして回収。旧プロセス停止を確認できなければ能動調査を開始しない。自動再開・旧PIDへのkillはしない          |
| 新しいPowerShellセッション   | 新合言葉・epochを使用。旧ownerがまだ稼働中なら監査はbusyとして新要求を送らない。終了後、過去結果をACL下の一覧から明示的に開き、採用は正本照合から再準備 |

ownerEpochは起動ごとの乱数とPython PID・生成時刻に結び付け、PID再利用を区別する。死んだownerの子を再接続して続行しない。Pythonだけが収集の中断を判定し、PowerShellだけが正本の採用状態を照合する。起動/受付の応答消失や古いstateは、mutex・ownerEpoch・重複台帳・結果ハッシュを検査して回復する。

### 8.4 APIの責務と再送

| API（すべて既存PowerShell窓口）                       | 再送・復旧の扱い                                                                                                              |
| ----------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------- |
| `POST /api/audit/runs`                                | 入力を検証して要求を保存し202。「受付未確認」を明示。Pythonが経路承認・キーを検証して受付/拒否を返す。別runとキー不一致は競合 |
| `GET /api/audit/runs/{id}` / `.../result`             | 所有セッションを照合。過去結果を開く操作では現在セッションの読取権を設定。存在するIDを知るだけではアクセス不可                |

| `POST /api/imports/prepare` / `GET /api/imports/{id}` | 元指紋・固定計画を保存し証跡準備を依頼。長い処理は202→状態取得。既存の採用記録があれば先に照合する                            |

ジョブ終了、証跡封印、JSON採用を別々に表示し、「収集完了」を「正本へ保存済み」と表示しない。再送で同じ結果へ収束させるが、共有をまたぐexactly-onceトランザクションを主張しない。IPC待ちでHTTP処理を止めず、Pythonが停止していても正本の読書き・pingを処理できることを受入条件にする。

定期監査は保存済みプロファイルの再実行と条件付きの前回比較から始める。無人実行、常設サービス、通知配信はMVPに含めない。

## 11. TDDと異常系を先に定義する開発手順

以下は実装時に作成するテストの計画であり、テスト・pytest環境を導入済みという記録ではない。

### 11.1 RED → GREEN → リファクタ

受入条件AUTO-01〜22をテストケースへ分解してから実装する。ケースにはID、前提、入力、注入する障害、期待する状態・副作用、検証層を付ける。

1. **RED**：次の小さな振る舞いについて、正常系に加え、関連する異常系・境界条件を書く。失敗が未実装または意図した仕様違反によるものか確認する。設定不備・fixture読込失敗だけのREDを実装の根拠にしない。
2. **GREEN**：その振る舞いを満たす最小の実装を行う。未観測を正常へ変える、期待値を緩める、例外を握りつぶす等で通さない。
3. **リファクタ**：状態遷移・型・責務の重複を整理し、同じテストで外部動作を維持する。保存機構・照合規則を別言語へ複製しない。関連テストと必要な契約テストを実行する。

変更の検証記録へケースID、意図したREDの理由、GREENの結果、整理した責務、未検証事項を残す。実装前の失敗を確認した事実がなければ、後付けテストをTDD実施済みと記録しない。テスト件数やカバレッジ率だけを合否基準にしない。

最初のDHCPルールのREDは、例えば次の期待から始める。キャプチャ成功は収集の成否であり、不正DHCP不在の根拠ではない。

```python
def test_dhcp_response_not_observed():
    result = evaluate_dhcp(observed_responses=[], capture_succeeded=True)
    assert result.status == "inconclusive"
```

その後にキャプチャ失敗、正規冗長、承認外、基準なしの順で小さなケースを追加する。評価APIの詳細が増えてもこの意味を維持する。正常データのテストだけを先に大量に通して異常系を後回しにしない。

### 11.4 不変条件と生成データ

通常の具体例に加え、次を生成データ・異なる順序・繰返し回数でも検証する。Pythonは固定seedを持つ生成fixtureをpytestで、TSはVitestで扱う。失敗したseedと最小化した入力を再現fixtureとして残す。初期導入はpytestだけとし、専用のプロパティベーステストライブラリーは必要性を確認して開発依存として検討する。

- 送信対象は常に許可したオンリンクIPv4一覧の部分集合で、除外IPとの積集合は空。入力CIDR/除外の順序や重複で範囲を広げない。
- 同じ採用を何度再送しても機器・証跡・監査結果は増えない。部分採用の重なりでも採用済みキーを二重生成しない。
- 証跡の検証前には正本の採用差分を保存しない。書込失敗なら旧正本の完全性を保ち、応答不明は成功にも未採用にも決めつけない。
- 採用→Undoで業務状態は採用前へ戻り、履歴はrevertedとして残る。revisionは戻さず、共有証跡を消さない。
- IPCの重複・順序変更・遅延で同じキーの収集を二重起動しない。キャンセル後に対象追加・新プロセス起動をしない。
- 観測の欠落・失敗・機能OFFを増やしても、それを根拠に評価が問題なしへ改善しない。

### 11.5 実行ゲートと検証記録

通常の検証はpytest＋既存の `bun run verify` を基礎にし、実行器を既定で送信不可の疑似実装へ差し替える。環境のNmap/TSharkが偶然見つかったことを理由に実行へ切り替えない。TSharkの `-r` による固定pcapのフィルター確認は、ツールがあるオフライン結合テストとして明示し、live captureと分ける。

Windows結合・現地試験は独立ゲートとし、モック成功で合格にしない。未導入・未実施のskipは理由付きで一覧化し、正式な現地監査のリリース条件では必要ゲートの未完了を残さない。実機試験は対象範囲・NIC・経路・ツール版・共有条件・実測結果を記録する。

実装段階で各AUTO条件にテストID・実装ファイル・実行結果・現地記録を対応付ける。本計画の作成時点では、その対応表を「テスト成功済み」で埋めない。
