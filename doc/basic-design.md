- プロジェクト名：tylan
- 作成日：2026-11-05
- 文書バージョン：0.4（共有への保存を起動用スクリプト tylan.cmd が受け持つ方式に変更）
- 前提文書：[要件定義 0.3](requirements.md)（以下「要件」。要件IDはそのまま参照する）

次期拡張は [現地LAN監査の自動収集・マッピング計画](audit-automation.md) を参照する（2026-11-06、未実装）。本書の現行構成を基礎に、非同期の収集ジョブ、Pythonと外部ツール、観測結果の独立形式、差分取り込みを追加する計画である。以下の「外部通信ゼロ」は現行版の仕様であり、拡張後もブラウザーの通信先はlocalhostだけとし、収集プロセスの社内向け通信を別に定義する。

## 1. 設計の要点

| 項目     | 決定                                                                                                                                |
| -------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| 保存形式 | **正本は監査ごとのJSONファイル（例：`network-2026.json`）**。SQLite・DBは使わない（2章）。                                          |
| 編集方式 | JSONファイルを作成・開いて直接編集し、確定した変更を自動保存する（5.2、10章）。                                                     |
| 認証     | アプリ内認証なし。アクセス制御は共有・NTFS権限のみ（要件2.4）。                                                                     |
| 配布物   | `editor.html`（編集）と、そこから生成する `viewer-*.html`（閲覧）。どちらもJS/CSS内包の単体HTML。                                   |
| 実行環境 | 編集は `tools\tylan.cmd`（PowerShell 5.1）が `127.0.0.1` で配信するEdge画面。閲覧は `file://` 直接起動。Node.js・常駐サーバー不要。 |
| 状態管理 | Svelte 5 runesで作業データを1つだけ持ち、一覧・台帳・図はすべてそこから導出する。                                                   |
| 検証     | Zodの構造検証＋参照・業務検証を1つの関数 `validate()` にまとめ、確定・読込・出力の全経路で通す。                                    |
| 外部通信 | 利用時ゼロ。CSPで閲覧用は `connect-src 'none'`、編集用は `'self'`（起動用スクリプトだけ）とし、仕組みでも塞ぐ。                     |

利用頻度は年1回の監査と臨時更新のみで、編集者は同時に1名という前提に合わせ、可動部品を最小にする。

## 2. 保存方式の決定：JSONかSQLiteか

### 2.1 結論

**JSONを正本とする。SQLiteは採用しない。**

### 2.2 比較

| 観点                              | JSON                                                       | SQLite                                                                                                                     |
| --------------------------------- | ---------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------- |
| `file://` のブラウザーで読む      | `JSON.parse` だけで済む                                    | sql.js等のWASM（約1MB）を単体HTMLへ内包する必要がある                                                                      |
| 共有上の原本への保存              | ダウンロードで丸ごと書き出す                               | ブラウザーからは共有上のDBファイルを直接更新できない。結局は丸ごと書き出しになり、部分更新・トランザクションの利点が出ない |
| 同時編集・ロック                  | なし（運用で1名に限定）                                    | 同じくなし。SQLite公式もネットワークファイルシステム上のロックは信頼できないとしている                                     |
| 機密性・改ざん防止                | 平文。NTFS権限で守る                                       | 同じく平文。暗号化しても鍵の置き場がない                                                                                   |
| 人による確認・復旧                | テキストなので、差分比較・目視・メモ帳での応急修正ができる | バイナリのため専用ツールが必要                                                                                             |
| 入力の安全性                      | Zodで全件を厳格に検証できる                                | 読んだ後に同じ検証が必要になり、手間が増えるだけ                                                                           |
| 想定規模（要件NFR-02、10MiB以下） | 全件をメモリーに載せても十分速い                           | 規模面の利点が出ない                                                                                                       |

SQLiteは、DBへ直接書けるプロセスが複数ある場合に価値がある。この構成ではブラウザーが共有上のファイルを直接開けないため、SQLiteにしても安全性・整合性は上がらず、依存と復旧の手間だけが増える。

### 2.3 JSON側で行う安全策

- 読込時に厳格なZodスキーマで全件を検証する。未知のキーは拒否し、文字数・件数・ネストを制限する。上限は10MiB（要件SEC-01、NFR-04）。
- `schemaVersion` が未対応のファイルは読み込まない（要件6.2）。
- 検証に通るまで現在の作業データを置き換えない（要件CRUD-09）。
- ファイル名に版と日時を入れ、`archive\` に旧版を残す。直前版へ必ず戻せる（要件2.3）。
- localStorage・IndexedDBには保存しない（要件SEC-08）。

### 2.4 見直す条件

次のいずれかが必要になった時点で、ホスティングなしという前提も含めて再設計する（要件1.2・10.2）。

- 複数人の同時編集、または共有上の原本への直接上書き
- 改ざんできない操作履歴、利用者の認証
- 10MiBを大きく超える規模、または他システムとのデータ連携

## 3. 全体構成

### 3.1 構成図

```text
[開発時]  Vite + Svelte 5 + TypeScript (bun)
            │ vite build --mode viewer   → .build/viewer/viewer-template.html（データなし）
            │ vite build --mode editor   → dist/editor.html（viewer-templateを文字列で内包）
            ▼
[共有フォルダ]  \\fileserver\network\tylan\
  tools\tylan.cmd ─▶ tylan.ps1（127.0.0.1）─▶ Edge で editor.html ── 自動保存 ──▶ working\network-2026.json
        │  公開
        ├─▶ published\viewer.html（旧版は archive\viewer-r0003-….html へ移動）
        └─▶ *.csv（保存先を選ぶ：台帳・ポート・監査・対応事項）
```

### 3.2 単体HTMLのビルド

- 単一バンドルにする。動的import・コード分割を行わず、モジュールのプリロードも無効にする。
- `build/standalone.ts` の自作プラグインを `vite.config.ts` から使う。出力されたJS・CSSを `<script type="module">` と `<style>` としてHTMLへ埋め込み、外部ファイル参照を残さない。インラインのモジュールスクリプトは外部ファイルを取得しないため、`file://` のCORS制約を受けない。
- 画像・アイコンはインラインSVG、またはdata URIにする。Webフォントは使わず、システムフォント（Yu Gothic UI、Meiryo）を指定する。
- 自作プラグインで不具合が出た場合は `vite-plugin-singlefile` に切り替える。
- ビルド後のチェックとして、出力HTMLに `src=`、`href=`（`data:` と `#` 以外）、`import(` が残っていないかをスクリプトで確認する（要件AC-02）。

### 3.3 閲覧用HTMLの生成

閲覧用HTMLは、データなしの雛形 `viewer-template.html` に公開用データを差し込んで作る。雛形は編集ツールのビルド時に `virtual:viewer-template` モジュールで文字列として取り込む。

```html
<script type="application/json" id="tylan-data">/*TYLAN_DATA*/</script>
```

差し込みの手順（要件SEC-03）：

1. 公開用の射影データを作る（9章）。
2. `JSON.stringify` した結果の `<`、`>`、`&`、U+2028、U+2029 を `\uXXXX` 形式に置き換える。JSONの構文上、これらは文字列の中にしか現れないため、意味は変わらない。
3. 雛形を目印 `/*TYLAN_DATA*/` で `split` する。ちょうど2つに分かれることを確認してから連結する。`String.replace` は `$&` 等を特殊扱いするため使わない。
4. 生成したHTML文字列から同じ要素を取り出して `JSON.parse` し、公開スキーマで再検証してから書き出す。

閲覧側は `textContent` を `JSON.parse` し、公開スキーマで検証する。失敗した場合は図を描かずにエラーを表示する。`type="application/json"` の要素は実行されないため、CSPのスクリプトハッシュにも影響しない。

### 3.4 CSP

両方のHTMLに `<meta http-equiv="Content-Security-Policy">` を入れる（要件SEC-09）。

```text
default-src 'none';
script-src 'sha256-<ビルド時に算出>';
style-src 'unsafe-inline';
img-src data: blob:;
connect-src 'none'（閲覧用）／'self'（編集用）;
base-uri 'none';
form-action 'none'
```

- スクリプトは、ビルド時に埋め込み済みスクリプトのSHA-256を計算して許可する。`'unsafe-inline'` は使わない。
- スタイルは、Svelte Flowがノード位置を `style` 属性で指定するため `'unsafe-inline'` を許可する。
- `file://` 上での有効性は、技術検証（要件10.1の手順1）でEdgeとChromeを使って確認する。

## 5. 状態管理とCRUD

### 5.1 作業データ

```ts
// store.svelte.ts（概念。実装はcreateWorkspaceごとに状態を分離）
let doc = $state.raw<Doc>(initialDoc) // 唯一の作業データ。凍結し直接変更を防ぐ
let saveState = $state<'clean' | 'dirty' | 'exportRequested'>('clean')
const undoStack: Doc[] = [] // 確定前のスナップショット

export function commit(mutate: (draft: Doc) => void): ValidationResult {
  const next = structuredClone(doc)
  mutate(next)
  const result = validate(next)
  if (result.errors.length) return result // 作業データは変えない
  undoStack.push(doc)
  if (undoStack.length > 10) undoStack.shift()
  doc = next // 実装では凍結してから差し替える
  saveState = 'dirty'
  return result
}
```

- フォームは対象エンティティを `structuredClone` した下書きを編集する。キャンセルすると下書きを捨てる（要件CRUD-02）。
- 確定・図上での接続変更・削除・状態変更は、すべて `commit()` を通す。検証を迂回して更新する経路を作らない（要件CRUD-03、8章）。
- 確定のたびに全件を検証する。想定規模（1,000機器・5,000監査結果）であれば数十ms程度で終わる見込み。重くなった場合は、変更したエンティティとその参照先だけを検証する方式に変える。
- Undoは確定直前の全体スナップショットを10世代まで保持する（要件CRUD-07）。JSONの再読込で破棄する。

### 5.2 起動用スクリプトと自動保存（要件2.2、CRUD-08）

EdgeのFile System Access APIは共有フォルダでのフォルダ選択を拒否し、ファイル単位でも書き込みの最後（一時ファイル `.crswap` の置き換え）で `InvalidStateError` になった。このため共有への読み書きは `launcher/tylan.ps1`（配布時は `tools\tylan.ps1`）が行う。

**起動用スクリプト（`tylan.ps1`、Windows PowerShell 5.1、ASCIIのみ）**

| 項目     | 内容                                                                                                                                                                                                                                                                 |
| -------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 起動     | `tylan.cmd` が `start` で `powershell.exe -WindowStyle Hidden -ExecutionPolicy Bypass -File tylan.ps1` を実行してすぐ閉じる（コンソールは一瞬だけ表示される）。起動失敗などの致命的なエラーは `trap` でメッセージボックスに出す。tylanフォルダは `tylan.ps1` の1つ上 |
| 待ち受け | `TcpListener(127.0.0.1, 空きポート)`。HTTPの解析は最小限で、1要求ずつ処理して接続を閉じる                                                                                                                                                                            |
| 合言葉   | 起動ごとに256ビットの乱数。`/?t=<合言葉>` でEdgeを開き、APIは `X-Tylan-Token` ヘッダーで照合する                                                                                                                                                                     |
| 検査     | Hostが `127.0.0.1:<ポート>` でない要求（DNSリバインディング）、Originが異なる要求、合言葉のない要求を403で拒否する                                                                                                                                                   |
| 対象     | `working`・`working/csv`・`published`・`archive` 内の `.json`・`.html`・`.csv` だけ。区切り文字・`..`・先頭のドットを含む名前は400                                                                                                                                   |
| API      | `GET /api/info`、`GET /api/list?dir=`、`GET /api/file?path=`（応答ヘッダー `X-Last-Modified`）、`PUT /api/file?path=&expect=`、`POST /api/copy?from=&to=`、`POST /api/ping`                                                                                          |
| 書き込み | 同じフォルダの一時ファイルへ書いてから `File.Replace`（失敗時はコピー）で置き換える。`expect` が直前の更新日時と違えば409、`new` で既存なら409、`any` は上書き                                                                                                       |
| 終了     | 3分間要求がなければ終了する。編集画面は10秒ごと（裏に回ると最短1分ごと）に `ping` を送る                                                                                                                                                                             |

**編集画面側（`folder.ts`、`file-session.svelte.ts`）**

| 操作                   | 動作                                                                                                                                       |
| ---------------------- | ------------------------------------------------------------------------------------------------------------------------------------------ |
| 起動                   | URLに合言葉がなければ「`tylan.cmd` から起動してください」と表示して止める。あれば `info` と `list` で接続する                              |
| 一覧から開く           | `working` 内の `.json` を新しい名前順に並べる。選んだファイルを検証し、通れば読み込む                                                      |
| 今回の監査用JSONを作る | ファイル名（初期値 `network-<年>.json`）と引き継ぎ元を選ぶ。引き継ぎ元は先に検証し、`expect=new` で書き込む                                |
| 自動保存               | `commit` 成功・Undoの約0.8秒後に書き込む。連続した変更は1回にまとめ、書き込み中の変更は直後にもう一度保存する。Ctrl+Sで即時保存            |
| 競合                   | 409が返れば自動保存を止め、「読み込み直す」か「上書きする（`expect=any`）」を選ばせる                                                      |
| 保存失敗               | 変更はメモリーに残したまま「保存できませんでした」と表示し、「今すぐ保存」で再試行できる。スクリプトが終了していれば起動し直すよう案内する |
| ファイルを閉じる       | 未保存分を保存してから一覧へ戻る。保存できなければ閉じない                                                                                 |
| 閲覧用HTMLを公開       | 既存の `published/viewer.html` を `archive/viewer-r<旧版>-<日時>.html` へ写してから、新しい `viewer.html` を書き込む                       |

| 表示                                                       | 意味                        |
| ---------------------------------------------------------- | --------------------------- |
| 未保存の変更（まもなく自動保存）                           | `commit` 済みで書き込み待ち |
| 保存中…                                                    | 書き込み中                  |
| 保存済み hh:mm:ss                                          | ファイルへの書き込みが完了  |
| 保存できませんでした／別の場所で変更されたため保存を停止中 | 利用者の操作が必要          |

保存のたびに `revision` を1増やす。未保存または保存中の状態での画面離脱は `beforeunload` で警告する。

### 5.3 削除（要件CRUD-05・06）

1. `findReferences(doc, id)` で、そのIDを参照しているポート・接続・IP・監査結果・対応事項・図の配置を列挙する。
2. 参照が1件でもあれば削除を止め、一覧と移動リンクを表示する。連鎖削除はしない。
3. 参照がない場合のみ、名称を示して確認したうえで削除する。
4. 機器の使用終了は `usage: 'retired'` などの状態変更で表し、物理削除とは別の操作にする。

例外として、機器を削除する際、配下のポートがどこからも参照されていなければ、ポートも同時に削除する。削除前の確認画面に件数を表示する。

## 6. データ設計（正本JSON）

### 6.1 トップレベル

```json
{
  "format": "tylan",
  "schemaVersion": 1,
  "project": {
    "id": "prj_…",
    "name": "…",
    "description": null,
    "revision": 4,
    "baseRevision": 3,
    "appVersion": "0.1.0",
    "createdAt": "2026-11-05T14:30:00+09:00",
    "updatedAt": "…",
    "updatedBy": "山田",
    "surveyDate": "2026-11-05"
  },
  "sites": [],
  "locations": [],
  "devices": [],
  "ports": [],
  "links": [],
  "segments": [],
  "ipAssignments": [],
  "dhcpScopes": [],
  "wirelessNetworks": [],
  "auditTemplate": { "version": "2026-11", "items": [] },
  "auditRounds": [],
  "auditResults": [],
  "evidence": [],
  "actionItems": [],
  "layouts": [],
  "publishSettings": { "siteIds": [], "fields": {} }
}
```

- エンティティは種類ごとの配列で持ち、IDで互いに参照する。ネストさせない。
- 多対多の関係は、片側にIDの配列で持つ。SSIDとAPは `wirelessNetworks[].apDeviceIds`、ポートとVLANは `ports[].segmentIds` とする。
- 監査マスターもJSONに含め、ファイル単体で内容が完結するようにする。

### 6.2 ID

- 形式は `接頭辞_ランダム16文字`（例：`dev_k3x9…`）。`crypto.getRandomValues` で生成する。`randomUUID` はセキュアコンテキストが必要なため使わない。
- 接頭辞は `sit`、`loc`、`dev`、`prt`、`lnk`、`seg`、`ip`、`dhc`、`wln`、`rnd`、`aud`、`evd`、`act`、`lay` とする。読み込み時は接頭辞と参照先の種類が一致するかも検証する。
- 監査No.（1〜8、12〜23）はマスター内のキーであり、結果のIDとは別に扱う（要件6.2）。

### 6.3 主なエンティティ（要件6.1の具体化）

要件6.1の属性はすべて持たせる。ここでは設計上の判断が必要なものだけを示す。

| エンティティ      | 設計上のポイント                                                                                                                                                                                        |
| ----------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Device            | `kind`：`serviceAdapter`、`switch`、`ap`、`repeater`、`pc`、`printer`、`nas`、`camera`、`attendance`、`iot`、`other`、`unknown`。`approval`、`usage`、`observation` は別々の属性にする（要件6.2）。     |
| Port              | `deviceId` を必須とする。`status`：`used`、`free`、`unknown`。`medium`：`copper`、`fiber`、`wireless`、`unknown`。                                                                                      |
| Link              | `a` と `b` の端点を持つ。端点は `{ deviceId, portId \| null }` または `{ unknown: "説明文" }` のどちらか。`kind`：`physical`、`wireless`、`logical`。`certainty`：`confirmed`、`estimated`、`unknown`。 |
| IpAssignment      | `portId` と `segmentId` を持つ。`mode`：`static`、`dhcp`、`unknown`。                                                                                                                                   |
| DhcpScope         | `serverDeviceId` または `serverUnknown`（説明文）。範囲・除外は `{ start, end }` の配列。リースは `{ value, unit }`。                                                                                   |
| WirelessNetwork   | 認証方式は列挙値で持つ。PSKの入力欄は作らない（要件SEC-06）。                                                                                                                                           |
| AuditResult       | `scope`：`summary`（拠点の総括）または `target`（対象別）。`target` の場合は `targetRef: { type, id }` を持つ。                                                                                         |
| EvidenceReference | 説明・管理番号・保管先は文字列のみ。ファイル本体は持たない。                                                                                                                                            |
| DiagramLayout     | `positions: { [deviceIdまたは不明端点キー]: { x, y, pinned } }`、`hidden: string[]`、`viewport`。                                                                                                       |

### 6.4 値の規則

- 不明な値は `null` で表す。空文字・0・ダミーIPで代用しない。未確認・対象外・意図的な未設定を区別したい項目では、`{ state: 'unknown' | 'na' | 'set', value }` の形を使う（要件6.2）。
- 日時は `+09:00` 付きのISO 8601、日付は `YYYY-MM-DD` で保存する。
- 文字列の上限は、名称が100文字、備考などの自由記述が2,000文字。配列の上限は要件NFR-02の規模の5倍を目安とする（例：devicesは5,000件）。
- IPv4・IPv6・CIDR・MACの書式チェックは自前の小さな関数で行う。依存は追加しない。

## 7. 検証設計

`validate(doc): { errors: Issue[]; warnings: Issue[] }` を、確定・図上での編集・読込・全出力で共通に使う。`Issue` は `{ code, message(日本語), path, entityId }` とし、画面上で該当する項目へ移動できるようにする（要件CRUD-04）。

| 段階            | 内容                                                                                                                                            | 結果の扱い       |
| --------------- | ----------------------------------------------------------------------------------------------------------------------------------------------- | ---------------- |
| 1. 構造         | Zodの `strictObject` で型・列挙値・長さ・件数・座標の有限値をチェック。未知のキーは拒否                                                         | エラー           |
| 2. 参照         | ID重複、参照先の存在と種類、ポートの所属機器と端点機器の一致                                                                                    | エラー           |
| 3. 業務上の禁止 | 自分自身のポートへの接続、同じ接続の重複、物理ポートの二重利用、DHCP範囲の開始と終了の逆転、監査判定ごとの必須欄、総括と対象別結果の矛盾（8.2） | エラー           |
| 4. 実環境の異常 | 同一セグメント内でのIP重複、DHCP範囲と固定IPの重なり、範囲がセグメント外、169.254.x.x、未確認の接続                                             | 警告（保存可能） |

- 冗長構成・ループ・複数リンクは、異なる有効なポート同士であればエラーにしない（要件AC-08）。
- 同じIPでもセグメントが違えば重複として扱わない。
- 警告や未確認が残っていても書き出しは止めない（要件6.2）。
- 読込は次の順で行う：ファイルサイズ確認（10MiB）→ `JSON.parse` → `format` と `schemaVersion` の確認 → `validate`。エラーが0件のときだけ、作業データを一括で置き換える。

## 8. 監査

### 8.1 マスターと回次

- 20項目は `audit-master.ts` の定数として持つ。No.9〜11は欠番のまま補完しない（要件5.2）。
- 回次を作成すると、拠点ごとに20件の `summary` 結果を、判定 `unchecked` で生成する（要件5.1）。
- 新しい回次を作っても、前回の判定は引き継がない。詳細画面で前回の結果を参照表示する（要件AUDIT-06）。

### 8.2 判定ルール（Zodの `superRefine` で実装）

| 判定                  | 必須欄                                     |
| --------------------- | ------------------------------------------ |
| `ok`（問題なし）      | 確認結果・確認者・確認日                   |
| `ng`（要対応）        | 上記＋問題点＋関連する対応事項1件以上      |
| `unchecked`（未確認） | なし。確認を試みた場合は理由・次の確認方法 |
| `na`（対象外）        | 対象外理由・確認者・確認日                 |

総括と対象別結果の整合（同じ回次・拠点・No.ごとにチェック）：

- 対象別結果に `ng` がある場合、総括は `ok` も `na` も不可。
- 対象別結果に `unchecked` がある場合、総括は `ok` 不可。

対象別の結果を変更しても、総括は自動では書き換えない。

### 8.3 集計とバッジ

- 集計の分母は総括20件とする。対象別結果の件数は別に表示する（要件5.1）。
- 図のバッジは関連する結果から1つを選んで表示する。優先順は `ng` → `unchecked` → `ok`。すべて `na` の場合のみ `na`、結果がなければ「監査記録なし」。複数ある場合は件数も表示する（要件AUDIT-05）。
- 対応事項を完了にしても、判定は自動では変わらない（要件AUDIT-03）。

## 9. 公開（閲覧用HTML）

- `toPublic(doc, publishSettings)` は、許可した項目だけを新しいオブジェクトに詰め直す（許可リスト方式）。全データを複製して不要な項目を消す方式は、項目の追加時に消し忘れが起きるため使わない（要件DATA-05）。
- 初期の許可項目は要件DATA-06のとおり。対象拠点外の機器を端点とする接続、除外した機器に紐づく監査結果も、参照関係ごと取り除く。
- 公開用のスキーマ `PublicDocSchema` も `strictObject` で定義し、出力前に検証する。許可していない項目が残っていればエラーにする。
- 生成前に、公開する件数と除外する項目をプレビュー画面で確認する。
- 閲覧用HTMLのヘッダーには、プロジェクト名、データ版、調査基準日、生成日時、アプリ版を表示する（要件2.1）。

## 10. ファイル入出力

| 操作           | 方式                                                                                                                                                                                                                              |
| -------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| JSON読込・保存 | 5.2のとおり、起動用スクリプト経由で `working` のJSONを開いて直接保存する                                                                                                                                                          |
| 閲覧HTML・CSV  | 閲覧HTMLは `published/viewer.html` へ公開（5.2）。CSVは `working/csv/` へ保存する                                                                                                                                                 |
| JSON           | `JSON.stringify(doc, null, 2)`。差分を見やすくするため整形して出力する。保存時に `revision` を1増やす                                                                                                                             |
| ファイル名     | 新規JSONの初期名は `network-2026.json`。出力物は `viewer-r0004-20261105-143000.html`、`assets-r0004-….csv`                                                                                                                        |
| CSV            | UTF-8 BOM付き、CRLF。値は必ず `"` で囲み、内部の `"` は2つ重ねる。先頭が `= + - @ \t \r` の値には `'` を付けて式として評価されないようにする（要件SEC-05）                                                                        |
| 監査CSV        | 先頭はマスターの列順（No.、分類、調査項目、確認内容、確認方法、判定、確認結果・現状、問題点・対応事項）。続けて拠点、対象、回次、確認者、確認日、証跡を出す                                                                       |
| PNG            | `html-to-image` で図のDOMを画像化し、ダウンロードする（画像生成に時間がかかり、保存先選択に必要な「クリック直後」の条件を満たせないため）。図名・拠点・データ版・凡例を枠内に描画する。印刷用には `@media print` の表示も用意する |

版の運用：開いた時に `baseRevision = revision` とし、保存ごとに `revision + 1` とする。他の場所での変更は5.2の更新日時確認で検出して保存を止める。排他ロックは作らない（同時編集は運用で避ける）。

## 11. 構成図

### 11.1 データから図への変換（`graph.ts`）

- ノードは、図から除外していない機器と、不明端点（`unknown:<linkId>:<a|b>`）から作る。不明端点は台帳には載せない（要件6.1）。
- 拠点・設置場所は、Svelte Flowの親ノード（グループ）として表す。
- エッジは接続から作る。線の種類は次のとおり（要件VIEW-03・09）。
  - 物理接続：実線
  - 無線：細い点線
  - 論理接続：灰色の破線
  - 推定・接続先不明：破線と「?」記号
- 矢印やアニメーションは付けない。
- 図ライブラリーの状態（nodes/edges）は毎回作業データから作り直し、正本としては扱わない。ドラッグした結果だけを `commit` で `layouts` に書き戻す。

### 11.2 見た目（要件4.2）

- ノードの大きさは種別にかかわらず統一する（例：幅200px）。種別アイコン、名称、主要IP、設置場所、確認状況、監査バッジを表示する。
- ズームが一定以下になったら、名称とバッジだけを表示する。
- 判定の色は、問題なし＝緑、要対応＝赤、未確認＝琥珀、対象外＝グレー。必ず文字・記号と一緒に表示する。
- 機器を選ぶと、その隣接ノードと接続を強調し、それ以外を薄くする。
- 絞り込みで対象外になった隣接ノードは薄く残し、「非表示の接続 n件」と表示する。
- Svelte Flow標準の `MiniMap`、`Controls`、`fitView` を使う。

### 11.3 自動レイアウト（`layout.ts`）

- サービスアダプタを起点に、物理接続を幅優先でたどって階層を決める。階層ごとに、親の並び順に合わせて左から並べる。到達しないノードは右端の「未接続」列に置く。
- 固定（`pinned`）したノードは動かさない。実行前に、移動するノードの数を示して確認する。実行後はUndoで戻せる（要件VIEW-06）。
- この簡易方式で線の交差が読みにくくなった場合は、`@dagrejs/dagre` を追加する。

### 11.4 閲覧専用モード

閲覧側では `nodesDraggable={false}`、`nodesConnectable={false}`、`elementsSelectable` は詳細表示のみに限定する。作業データを変更する経路そのものを持たない（要件VIEW-08）。

## 12. 画面

要件3.2の8画面を、編集ツールの左側ナビゲーションのタブとして並べる。画面遷移はハッシュ（`#/devices/dev_…`）で行い、ルーターライブラリーは使わない。

| 画面               | 主な部品                                                                                                |
| ------------------ | ------------------------------------------------------------------------------------------------------- |
| 開始・プロジェクト | tylanフォルダの選択、JSONの一覧・作成（前回分の引き継ぎ）・開く、拠点一覧、版、検証結果の件数、保存状態 |
| トポロジー         | 図、検索、絞り込み、凡例、詳細パネル                                                                    |
| 機器・資産台帳     | 一覧（検索・並び替え）、詳細、フォーム、関連へのリンク                                                  |
| ポート・接続       | 機器ごとのポート表、接続フォーム、図上での接続操作                                                      |
| ネットワーク設定   | セグメント、IP、DHCP、SSIDの各タブ                                                                      |
| 監査               | 回次選択、20項目の表、対象別結果、詳細フォーム                                                          |
| 対応事項           | 一覧、フォーム、関連する監査結果へのリンク                                                              |
| 検証・書き出し     | エラー・警告の一覧（クリックで該当箇所へ移動）、公開プレビュー、各種出力                                |

各画面は「一覧 → 詳細 → 編集 → 確定」の流れで統一する。一覧は共通の表コンポーネント1つで作る。

自由記述欄には「パスワード・PSK・資格情報は記入しない」と常に表示する（要件SEC-06）。表示はすべてSvelteのテキスト補間で行い、`{@html}` は使わない（要件SEC-02）。

## 13. テスト

2026-11-05に最新安定版を調査し、Vitest 5.1.0、`@vitest/browser-playwright` 5.1.0、`vitest-browser-svelte` 3.1.0を採用した。Biome 2.6.5でTypeScript・Svelte・CSS・HTMLを検査・整形する。調査元と実行方法は [実装・検証記録](implementation.md)。

- 開発時に `bun run test:unit`（Vitest / Node）で、以下の純粋関数を確認する。利用者の環境にはbunを要求しない。
  - `validate`：エラーと警告の区別、冗長リンクを拒否しないこと
  - `csv`：式の無害化、引用符・改行
  - `publish`：`</script>` を含む値で生成したHTMLから元データが復元でき、除外した項目が含まれないこと
  - 往復テスト：読込 → 書き出し → 再読込で内容が同じになること
  - 自動保存：作成 → 変更 → 開き直しで復元し、他所で変更されたファイルは上書きしないこと（Browser Mode、フォルダはメモリー上の代替実装）
  - 起動用スクリプト：実際の `tylan.ps1` を起動し、合言葉・Host・Origin・フォルダ制限・競合の拒否と、編集画面からの保存・公開・CSVが日本語と空白を含むフォルダへ届くこと（配布物テスト）
- 画面と配布物の確認は、要件9章の受入条件（AC-01〜12）を手順書にして、実際の共有フォルダ上で行う。
- `bun run test:browser` は実Chromiumでフォーム・キャンセル・下書き離脱保護・Undo・監査回次作成を確認する。runesのテストは `.svelte.test.ts` とし、Svelteコンパイラーを通す。
- `bun run test:release` はビルド済みHTMLをサーバーなしの `file://` で開き、通信なしの起動・XSS対策・PNG・同版のJSON/HTML出力を確認する。インストール済みの場合は実Edgeでも起動する。
- `bun run verify` はBiome → 型チェック → Node/Browserテスト → ビルド → 配布物テストの順で実行する。
